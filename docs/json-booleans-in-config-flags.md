# JSON booleans in config flags

**System-scoped.** This is about every boolean-shaped flag the product reads
out of a JSON config file — a collector's `disable`, an api key's `disabled` /
`_disabled`, and any flag reader added after them. It is not about one ticket;
the ticket that produced it (a hunt finding) is only the first place the shape
bit.

## The claim

**A JSON `false` is not a Perl false.** `Developer::Dashboard::JSON::json_decode`
is `JSON::XS->new->utf8->decode(...)`, and JSON::XS decodes the literals `true`
and `false` as `JSON::PP::Boolean` objects — blessed references. They numify,
stringify and boolify correctly (`false` is `0`, `"0"`, and false in boolean
context), but **`ref($value)` is true for both of them**. A reader that asks
"is this a reference?" before it asks "is this false?" cannot tell `false` from
`{}`.

Measured on the tree (JSON::XS 4.04):

```
$ perl -Ilib -MDeveloper::Dashboard::JSON=json_decode -e '
    my $d = json_decode(q({"disable":false,"on":true,"n":0,"s":"false"}));
    for my $k (qw(disable on n s)) { my $v = $d->{$k};
      printf "%-8s ref=%-18s is_bool=%d str=%s bool=%s\n", $k, ref($v)||"(none)",
        JSON::XS::is_bool($v)?1:0, "$v", ($v?"T":"F") } '
disable  ref=JSON::PP::Boolean  is_bool=1 str=0 bool=F
on       ref=JSON::PP::Boolean  is_bool=1 str=1 bool=T
n        ref=(none)             is_bool=0 str=0 bool=F
s        ref=(none)             is_bool=0 str=false bool=T
```

Two things in that table matter to every flag reader:

- `disable: false` arrives as a **reference** whose boolean value is false.
- the **string** `"false"` is true in Perl (it is a non-empty string), so a
  reader cannot rely on Perl truthiness either — it needs a token test.

## Where the shape enters

Every value that comes out of `json_decode` may carry a boolean object, so
this is a property of the whole config layer, not of two subroutines. On the
tree at the time of writing, `json_decode` has 46 call sites across 19 modules
under `lib/`, and **nothing in `lib/` or `t/` unwraps a boolean** (no
`is_bool`, no `JSON::PP::Boolean`, no `Types::Serialiser` reference exists).
A value that is only ever tested with `if ($value)` is fine; a value that is
tested with `ref($value)` first is not.

## The two readers that exist today

Both live in `Developer::Dashboard::Config` and both had the same shape:

| reader | called from | for the key |
|---|---|---|
| `_collector_disable_flag` | `_normalize_collector_job` | a collector's `disable` |
| `_api_key_disabled_flag` | `_normalize_api_keys` | an api key's `disabled` / `_disabled` |

Their order of tests was: undefined → not disabled; **any reference →
disabled**; one of the tokens `0 / false / no / off` (case-insensitive) → not
disabled; any other non-empty value → disabled.

The reference test is deliberate and stays. An array or hash under the key
(`"disable": {}` or `"disable": []`) means somebody wrote *something* there,
and the safe reading of "something" is disabled — `t/93-config-coverage.t`
constrains exactly that. The defect is only that a boolean object is *also* a
reference, so `"disable": false` — the most natural way to write "not
disabled" in JSON — read as disabled. `"disabled": false` on an api key did the
same, and `_normalize_api_keys` then dropped the key from the loaded set as if
it had been tombstoned.

## The rule

**Unwrap a JSON boolean before any reference test, and only a JSON boolean.**

```perl
use JSON::XS ();
...
$value = $value ? 1 : 0 if JSON::XS::is_bool($value);   # first
return 1 if ref($value);                                # then the existing tests
```

- `JSON::XS::is_bool` answers true only for the objects JSON::XS itself
  produces. Do not widen it to `Scalar::Util::blessed` — that would turn any
  blessed object under the key into a plain 0/1 and lose the
  reference-means-disabled reading.
- After the unwrap the value is a plain `1` or `0` and falls through the
  existing token test, so `false` and `0` and `"false"` and `"no"` all land in
  the same place without a second special case.
- Array and hash references are still disabled. Nothing about that changes.

### The accepted forms, after the rule

| written in config | reads as |
|---|---|
| key absent, or JSON `null` | not disabled |
| JSON `false` | not disabled |
| `0`, `"0"`, `"false"`, `"no"`, `"off"` (any case) | not disabled |
| `""` | not disabled |
| JSON `true` | disabled |
| `1`, `"1"`, `"yes"`, `"on"`, any other non-empty string | disabled |
| an array or an object | disabled |

## Who writes these flags

`Developer::Dashboard::CLI::API` tombstones a removed key as
`{ disabled => 1 }` — a numeric 1, never a JSON boolean — so the product's own
write path never produced the failing shape. The defect bites config a person
wrote or generated by hand, which is also the config nobody re-reads through a
dashboard command before trusting it.

## How to check a reader

- The unit that catches it is a normalisation call with `JSON::PP::false`
  (the same object JSON::XS returns) in the flag and an assertion that the
  collector is not disabled / the api key survives. `t/93-config-coverage.t`
  carries those assertions for both readers.
- Reproduce end to end in a `developer-dashboard:latest` container, never on a
  real board: write `"disable": false` on a collector in the layer's
  `config.json`, start collectors, and confirm the collector runs. The same
  with `"disabled": false` on an api key and `dashboard api ls`.
- When adding a new flag reader: decide what a reference means for that flag
  *before* writing the `ref()` line, and put the `is_bool` unwrap above it.
