# A proxy that defers execution can be forced to execute by accident

A chainable proxy exists to let a caller build up a command across several method
calls before anything happens: `thing->foo->bar->baz`. Nothing can run at `foo`,
because a second call may be coming. So the object has to hold its state and
decide, later, that the chain has ended.

**That decision is the whole design.** Everything else — accumulating words,
forwarding arguments — is bookkeeping. The question worth all the attention is
*what counts as the end*, and the tempting answer is the dangerous one.

## Why "execute when stringified" is a trap

The natural terminal condition is: run when somebody actually needs the value.
In Perl that means `use overload` with a stringify handler, and it reads well —
`print $proxy` does the thing, so does `"$proxy"`.

It also means the proxy runs in places nobody was thinking about:

- **a boolean test** — `if ($proxy) { ... }` asks for truth, and truth can be
  derived from the string
- **a numeric comparison** — `$proxy == 0`; perl's `overload` documentation notes
  that stringify is **autogenerated from numify** when absent, and that with
  `fallback` enabled some operators carry more than one semantics
- **interpolation into a diagnostic** — `warn "got $proxy"`, which is the worst
  one, because the message exists precisely when something has already gone
  wrong, and now the error path performs a side effect

An accidental execution that happens to *succeed* leaves no error behind. So the
failure is invisible in exactly the case a test looking for exceptions would
check.

## What to assert

**Assert the absence of the side effect, not the absence of an error.** Give the
proxy a target whose execution is observable — a command that appends to a
sentinel file — build one, use it in each incidental context, and assert the
sentinel is still absent:

```
{ my $p = build_proxy();  if ($p) { } }        # truth
{ my $p = build_proxy();  my $n = $p == 0; }   # numeric
{ my $p = build_proxy();  my $s = "x$p"; }     # interpolation
ok( !-e $sentinel, 'an un-terminated proxy performed no side effect' );
```

A test that only checks "no exception was thrown" passes for a proxy that ran
successfully every time.

## Three more properties worth pinning before you build

**`DESTROY` must not become a subcommand.** A method-missing handler receives
`DESTROY` like any other name unless it declines it explicitly. In a proxy that
accumulates method names into a command, that turns garbage collection into an
invocation. Assert that a proxy going out of scope un-terminated invokes nothing.

**The existing single-call form must not change.** A proxy is usually retrofitted
onto something that already returns values directly for the one-call case. That
behaviour has callers; it is the thing people already depend on, and it is easy
to lose while making the chained case work.

**Decide what a non-zero exit does, deliberately.** If the underlying runner dies
on failure and discards what the command printed, a chained call inherits that —
and a caller who chained three words gets an exception instead of the output the
command produced before failing. That may be right, but it should be a decision
rather than an inheritance.

## The general shape

The reason this class bites is that **the accumulate step is obvious and the
terminate step is invisible.** A design review reads the chaining, agrees it
works, and never asks what happens when the object is merely *looked at* — which
is the only moment the language decides for you.

Write the terminal condition down before implementing it, and say which
incidental contexts it deliberately does *not* fire in. If that list is empty,
the language has chosen for you and it will choose badly.
