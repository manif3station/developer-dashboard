# How testing works

## What testing is here

Tests are written first, before the implementation exists. The tests
cover the whole feature: every requirement, every edge case, every
acceptance criterion. They are expected to fail, because nothing is
implemented yet. Only test code is written, never the implementation:
test files live in `t/`, and nothing under `lib/`, `share/` or `bin/`
is touched.

A test that passes before the implementation exists is a bad test. A
test that fails for the wrong reason is a bad test. Both get fixed
before the branch moves on.

## The flow, step by step

1. The manager gives the scope and the acceptance criteria.
2. The understanding is reflected back in the tester's own words.
   The manager says whether it is right or wrong. Nothing is written
   until the understanding is confirmed.
3. The failing tests are written on a branch, `test/<topic>`, from
   the current master. One commit per delivery, test code only.
4. The manager checks the tests fully cover the acceptance criteria:
   every criterion has at least one test, and each test fails for the
   right reason. Gaps go back for more tests.
5. The branch goes to the developer only when the developer has
   capacity. The developer must never change the tests. The
   developer's work is done only when the implementation passes all
   of the tests.
6. The pull request is the developer's call. Neither the manager nor
   the tester creates it. The developer writes the code, runs the
   tests, and opens the pull request when nothing fails.
7. After the pull request opens, the tests are re-run as a double
   check: the proof set is run again on the pull request head, and
   anything the developer added or changed is checked against the
   scope. Anything beyond scope, or any acceptance criterion that was
   never given, goes to the manager to judge.
8. After every new push, the tests are re-run, and the scope is
   checked again. The manager replies to the reviewer as needed and
   gets a second review after any fix.
9. When an investigation finishes, the result goes to the manager and
   the developer does not start implementing. The manager verifies
   the result against the evidence and decides: a real defect becomes
   a planned item (failing tests first, branch to the developer at
   capacity); a cause that is not settled is held in triage and the
   developer moves to the next ready item.

## The test file form

Every test file follows the same shape:

- `use strict; use warnings;` at the top.
- `use FindBin` plus `use lib` pointing at the checkout's `lib/`,
  so the file loads the fresh checkout code.
- `use Test::More;` and `done_testing();` at the end.
- A full POD block after `__END__`, with `=head1 NAME`, `PURPOSE`,
  `WHY IT EXISTS`, `WHEN TO USE`, `HOW TO USE`, `WHAT USES IT` and
  `EXAMPLES`. The release-metadata test (`t/15`) requires all six
  sections plus `__END__` and `NAME` on every file under `t/`, and
  any test path cited in the POD must exist.

## Running the tests

- Run one file with `make test TEST_FILES=t/xxx.t`, with
  `PERL5LIB` set to the checkout's local library
  (`PERL5LIB="$PWD/local/lib/perl5"`). `prove -l` without blib
  fails, because the XS bundle is not loaded. For a verbose run, use
  `prove -Iblib/lib -Iblib/arch`.
- Direct `perl` runs of repo scripts need `-Iblib/lib -Iblib/arch`
  plus the same `PERL5LIB`, or the XS bundle is not loaded.
- After switching branches, the first `make test` may stop with
  "Makefile has been rebuilt, please rerun". Rerun it.
- `.dd-perl5lib-runner.pl` is generated by `perl Makefile.PL`
  (with `PERL5LIB` set; plain `perl Makefile.PL` fails because
  `File::ShareDir::Install` is not in the system perl's path). It is
  untracked and needed. Leave it in place.
- Untracked build artefacts appear in the repo after `make test`
  (`Dashboard.bs`, `HtmlEscape.c`, `.cover_db.*`). They are normal
  byproducts. Leave them.

## Verifying red

A new test file is run before the implementation exists, and the
split is recorded: how many checks fail, and that every failure is
for the missing behaviour, with the controls passing. A test that
fails for another reason is a test bug, not a red test.

When a test goes red against code that already exists, check first
whether the test misread the behaviour, and fix the test. Two
examples of that mistake: expecting lines matched before a NUL byte
to survive when the code returns an empty list for a binary file
(the file contributes nothing), and expecting forward-slash paths
when the Windows path normalisation is active under a mocked
Windows check. If the test is right and the code is wrong, that is a
real gap: report it to the manager, who decides what happens next.
Never pass a finding straight to the developer.

## Coverage

`Devel::Cover` on all four metrics is mandatory for every change:
statement, subroutine, branch and condition must all read 100.0.
Measure with:

```sh
cover -delete
HARNESS_PERL_SWITCHES=-MDevel::Cover prove -lr t
cover -report text -select_re '^lib/' -coverage statement -coverage subroutine -coverage branch -coverage condition
```

The `cover` binary lives in `local/bin/`. A stale `cover_db/` from
another `Devel::Cover` version fails to read; delete it and re-run.
For one file, run the same commands with that file in place of
`prove -lr t`.

Cover both sides of every two-outcome condition. Conditions that no
input can reach are annotated in the product code with
`# uncoverable branch` or `# uncoverable condition`. That annotation
is a product-code change, so it is not a testing decision.

## The Jenkins proof

Every test run goes through Jenkins with a build number. Anything
off Jenkins is a violation. The proof runs on all five legs
(`d2-amd64-tester`, `d2-arm64-fast-tester`, `macos`, `windows`,
`windows-arm64-sandbox`); a 5-file proof set is 25 runs, a 10-file
set is 50. Never trigger, stop, or change a build.

The local run proves the tests are written right. The Jenkins proof
proves they pass everywhere. Both are needed: a test that passes
locally and fails on one leg is a real finding, not a Jenkins
problem.

## The double-check

When a pull request opens, re-run the proof set on the pull request
head locally and confirm the tests pass, then check the scope: the
test files must be byte-identical to the tester's commits, the
implementation diffs must all fall inside the assigned scope, and no
new acceptance criterion may have been added. Existing-test updates
that only change form are fine; an update that changes what is
asserted is a judgement call for the manager, not a scope breach by
itself. Report what was checked, mapped item by item to what was
asked. Never just "done" with evidence.

## Windows patterns

- The `timeout` binary: the test helper looks for a file named
  exactly `timeout` and requires Perl's `-x`, which is false for a
  file with no extension on Windows. Also try `timeout.exe` and
  `gtimeout.exe` on Windows, and accept a candidate only when
  `--version` reports GNU, so the Windows `timeout.exe` in
  `system32` is skipped and Git's is found.
- A follow process that outlives its timeout holds the test's
  stdout and stderr pipes open, so `prove` never sees EOF and hangs.
  GNU timeout on Windows returns 124 but does not reliably terminate
  a native Strawberry Perl process. After a follow test's timeout,
  kill the process tree on Windows (`taskkill /T /F`), before the
  assertions. Windows-only, and never a product change.
- Symlink tests skip when symlink creation needs privileges.
  Unreadable-directory tests skip on Windows and as root, where
  `chmod 0000` does not make a directory unreadable.
- Mocking `is_real_windows` is legitimate only for pure-Perl code
  (the native grep fallback), where only the dispatch gate is
  platform-specific. Windows-API functions (the `Watch.pm`
  `_windows_*` functions and the Platform ACL functions) can never
  run on Unix and must not be pretended to be covered.
- `chmod` and `stat` mode bits do not work the Windows way: on
  Windows, Perl's `chmod` does not set Unix mode bits and `stat`
  synthesises 0777. Verify ownership with the Windows calls, not
  with `chmod` plus `stat`.

## Mocking and fakes

- Localise an imported sub in the module's own package, so the mock
  only applies inside the test:
  `local *Package::command_in_path = sub { 0 };`
- Put a fake binary first on PATH: a script that exits 1 whatever it
  is asked (named `grep` on Unix, `grep.bat` on Windows, found
  through `PATHEXT`), or a fake `d2` that just exits 0 when only its
  path is resolved.
- Localise `*STDIN` to a scalar handle to feed standard input.
- Build temp trees with `File::Temp`, and keep each test's tree
  separate when a later addition must not change an earlier count.

## Traps that have bitten before

- `Capture::Tiny`'s third return is the raw wait status. Shift
  right by 8 to get the exit code. A child that exits 1 produces
  256, not 1.
- A test helper that concatenates stdout and stderr and then
  JSON-decodes the result dies on any stderr warning. Keep stderr
  separate from decoded output.
- `perl -c` on a test file needs `PERL5LIB` exported first.
- A file whose name holds a colon-digit pattern (for example
  `x:12:y.txt`) breaks a naive `:digits:` parser: the first match is
  not the file boundary. The parser must try the next match.
- A duplicate file in grep output must be returned once, not twice.
